## 第 1 章 先把被测环境跑起来（这步错了后面全白做）

### 1.1 正常启动（脚本一键拉起）

双击项目根目录 `start.bat`。等 10 秒后验证：

```bash
curl http://127.0.0.1:8000/health
```

返回类似 `{"status":"ok","version":"4.0.0",...}` 就对了。浏览器开 `http://127.0.0.1:5173/login`，用 `tester / tester123` 登录，能进首页（新任务页）。

### 1.1b 不用脚本，手动启动

想自己控制后端前端的启动顺序、或者脚本跑不起来时，开两个命令行窗口分别跑：

**第一个窗口（后端）：**
```cmd
cd D:\nexus-agent\agent-core
"D:\software\Python 3.10.11\python.exe" run_server.py
```
> 注意：Python 路径里有空格，必须用双引号包起来，直接写会报"'D:\software\Python' 不是内部或外部命令"的错误。

**第二个窗口（前端）：**
```cmd
cd D:\nexus-agent\frontend
npm run dev
```

两个窗口都不要关。后端启动成功会看到 `Uvicorn running on http://127.0.0.1:8000`，前端启动成功会看到 `Local: http://127.0.0.1:5173/`。然后同样 curl /health 验证、浏览器开登录页。

### 1.2 起不来怎么办（降级启动）

`/health` 一直转，多半是本机 MySQL 3307 或 Redis 没响应。别死磕，先降级：

Git Bash：
```bash
cd "D:/nexus-agent/agent-core"
export MYSQL_PORT=33999
export DB_FALLBACK_SQLITE=1
export AGENT_MODE=mock
"D:\software\Python 3.10.11\python.exe" run_server.py
```

CMD 黑窗口：把三行 `export` 换成 `set MYSQL_PORT=33999` / `set DB_FALLBACK_SQLITE=1` / `set AGENT_MODE=mock`，其余一样。

- `DB_FALLBACK_SQLITE=1`：数据库自动降级到 SQLite，不依赖 MySQL。
- `AGENT_MODE=mock`：大模型走 mock，不需要 DeepSeek Key，压测和自动化结果稳定。
- `MYSQL_PORT=33999`：让它连不上 MySQL 从而快速走降级分支，不卡在连接超时。

前端照常 `npm run dev`（在 `D:/nexus-agent/frontend` 目录）。业务接口能通就能做后面全部实验；`/health` 偶尔空返回不影响接口测试。

> 记一句给面试官：**本地环境没起 MySQL/Redis 时用 SQLite + mock 模式降级，CI 里也是这么配的**（见第 06 篇）。

## 第 2 章 测试方案是什么、怎么写

### 2.1 一句话说明白

测试方案 = 开工前先写清楚：**测什么、不测什么、怎么测、什么算通过、什么时候算做完**。实习生写 1 页就够，不要写成论文。

### 2.2 直接抄这个模板

在 `software test/` 下新建 `测试计划书.md`，内容按下面填：

```markdown

灵枢 AgentHub v4.0，AI 智能体对话平台。
```

## 第 3 章 用例怎么设计（重点，简历数字从这来）

### 3.1 为什么是 136

```
接口用例：24 个接口 × 至少 2 条（1 正常 + 1 异常） + 鉴权/越权/注入补充 = 85 条
功能用例：9 个页面 × 主要操作链路 + 边界/异常 = 51 条
总计 136 条
Postman 集合：25 个请求按依赖顺序排列（后端 24 接口 + 多拆一个 admin 登录拿两套 token），每个带断言，Newman 能批量跑
```

面试官问「多少条」，就说：接口 85 条、功能 51 条，总共 136 条。接口覆盖了 24 个接口的正常流程、鉴权、异常参数、横向越权、Prompt 注入五个维度。

### 3.2 四种设计方法在本项目怎么用

**等价类**：把输入分成「有效」和「无效」两类，每类挑一个代表。
例：登录密码 = 正确密码（有效）/ 错误密码、空密码（无效）。3 条就覆盖了一堆组合。

**边界值**：卡在限制条件的边上。
例：对话目标要求 2~500 字 → 测 1 字、2 字、500 字、501 字。

**场景法**：按用户真实操作串一条链路。
例：`登录 → 新任务页选智能体 → 发目标自动执行 → 敏感词触发门禁 → 授权继续 → 下载交付物 → 定时任务建→跑→停→删`。

**错误猜测**：凭经验猜哪里容易出 bug。
例：快速连点两次发送（按钮有没有防重入）、断网后重连、停用的智能体能不能选来发对话、admin 不能删自己。

### 3.5 用例表怎么落地

在 `software test/` 新建 `用例表.md`（或 xlsx），接口测试和功能测试各一张表。

**接口测试表固定 8 列**：
```
用例编号 | 标题 | 前置条件 | 操作步骤 | 预期结果 | 实际结果 | 优先级 | 是否通过
```

**功能测试表固定 5 列**：
```
用例 | 测试方法 | 操作步骤（带序号） | 预期结果（带序号） | 优先级
```

填的时候注意：
- 「实际结果」必须是**你真跑完之后**填的，不要提前写「通过」；
- 失败的写清楚返回码和返回体，第 05 篇提缺陷要直接抄这一格；
- 编号连续，别跳号，面试官会数。

## 第 5 章 常见坑

1. **把所有用例写成接口用例**：功能测试和接口测试是两回事，功能测试是点页面看效果，接口测试是直接调后端。
2. **功能测试里写 F12 / Network**：功能测试是用户视角，不说技术操作，说"点哪个按钮、页面长啥样"。
3. **边界值只测上界不测下界**：只测 501 字不测 1 字，面试官一问就卡。
4. **环境没起就写用例**：先按第 1 章跑通，很多预期结果要看着真实返回填。
5. **忘了测横向越权**：普通用户不能看别人的数据，这个比纵向越权（普通用户不能调 admin）更隐蔽。

### 前 10 个 · 通用高频（牛客/超级简历/掘金/CSDN 高频出现，按频率排序）

#### Q01｜你们项目测试流程是什么？

整体分这几个阶段：

1. 需求阶段：先看需求文档，有歧义的地方提前和产品、开发沟通对齐，避免理解不一致。
2. 测试准备：编写测试计划，明确测试范围、验收标准；再设计测试用例，优先接口，再做页面功能。
3. 执行测试：环境就绪后先用 Postman 调试接口，接口通了再跑 pytest 自动化；发现 bug 提单，开发修复后我做回归。
4. 收尾上线：全部验证通过后做压测，整理测试报告；同时配置了 CI，代码提交自动跑自动化，失败直接告警。

#### Q02｜测试用例你怎么设计的？用了哪些方法？

主要用四种方法搭配设计：

1. 等价类：区分有效、无效输入，挑选代表性场景，比如密码正确、错误、空值。
2. 边界值：重点测临界值，比如输入限制 2~500 字，测 1、2、500、501。
3. 场景法：串联用户完整操作链路，比如登录→发任务→授权→下载交付物。
4. 错误猜测：结合经验，预判容易出问题的场景，比如短时间重复点击发送。

#### Q03｜登录功能你怎么测的？

我从四个维度去测：

1. 正常场景：账号密码正确，成功登录，拿到 token。
2. 异常场景：密码错误、账号不存在、账号/密码为空，校验提示信息。
3. 边界场景：密码长度刚好到最短、最长限制。
4. 安全 & UI：防暴力破解、验证码一次性；回车能不能触发登录。

#### Q04｜HTTP 常见状态码说几个？

分成三类好记：

1. 2xx 成功：200 请求成功
2. 4xx 客户端问题：400 参数错误、401 未登录、403 无权限、404 找不到资源
3. 5xx 服务端问题：500 服务内部报错、502 网关异常、503 服务不可用、504 超时

#### Q05｜接口测试和 UI 测试有什么区别？

主要从 3 个方面区分：

1. 测试对象：接口测试直接调后端接口；UI 测试是在页面上点点操作。
2. 能测的内容：接口可以测底层参数校验、越权、数据一致性、注入这类安全问题；UI 侧重页面展示、跳转、前端拦截。
3. 稳定性：接口自动化更稳定；UI 自动化很容易因为页面改动失效，维护成本高。所以我们项目接口用例写得多，UI 只保留核心链路。

#### Q06｜接口的异常用例你一般测什么？

主要四块：

1. 参数异常：空值、超长内容、特殊字符、类型传错
2. 鉴权异常：无 token、伪造/过期 token、越权访问
3. 业务异常：重复提交、查询已经删除的数据
4. 安全异常：Prompt 注入、SQL 注入、XSS

#### Q07｜断言你怎么写的？

三层校验：

1. HTTP 状态码校验：判断是不是符合预期，比如成功 200、无权限 403
2. 业务码校验：后端自定义 code，区分参数错误、注入拦截等不同业务报错
3. 返回字段校验：校验接口是否返回必须的关键字段，比如 token、用户名

#### Q08｜Postman 里接口之间有关联怎么办？

核心就是用环境变量传递参数，分两步：

1. 前置接口拿到返回值，在 Tests 脚本里把 token、id 存到环境变量
2. 后续依赖接口，header 或者 url 里直接引用这个变量
整套集合要按顺序跑，如果跳着跑，变量没拿到，接口就会报错。

#### Q09｜发现 bug 之后怎么处理？

分三步：

1. 先复现确认：反复操作，排除环境、操作问题，确认是真实 bug，不是需求本身就这样。
2. 提交缺陷单：写清复现步骤、预期、实际结果、业务影响，划分严重等级。
3. 回归验证：开发修好之后，除了验证这个 bug 本身，还要检查关联模块有没有受影响。

#### Q10｜回归测试你怎么跑的？

根据 bug 严重程度分三种策略：

1. P0/P1 高优先级 bug：验证修复点 + 关联模块整条链路复测
2. P2 低优先级 bug：只针对性测这个功能本身
3. 核心模块改动（权限、调度器）：全量自动化用例跑一遍

### 后 10 个 · AgentHub 项目实战追问

#### Q11｜你这个项目一共多少接口？覆盖得怎么样？

一共 24 个接口，分成 7 个模块。覆盖我分三块：

1. 接口用例 85 条：每个接口都覆盖正向、鉴权、异常场景
2. 管理员接口重点测三层权限：未登录、普通用户、管理员账号
3. 额外安全场景：Prompt 注入、横向越权；手工功能用例 51 条，多种用例设计方法都用到了

#### Q12｜最核心的 send 接口你怎么测的？

分两大类场景：

1. 正向场景：输入合规任务，校验正常返回回答，内容不为空
2. 异常场景：内容太短/超长、各类注入语句、token 异常、横向越权；每一条同时校验状态码和业务码，注入场景要拦截不能正常执行

#### Q13｜横向越权你测了什么？为什么比纵向越权重要？

我测了 3 个核心场景：查看别人会话、停用别人定时任务、下载别人交付物。

两者风险对比：

1. 纵向越权：普通用户访问管理员功能，前端页面一般直接拦截
2. 横向越权：访问同级别其他用户的数据，前端拦不住，只能靠后端校验，更加隐蔽，风险更高

我们后端统一返回 404，不会暴露这个资源真实存在。

#### Q14｜定时任务接了真实调度器，你怎么测的？

主要测整条生命周期：

1. 基础功能：新建每分钟触发的任务，等待 2-3 分钟，看是否正常执行、生成记录
2. 状态流转：新建、正常触发、停用后不再执行、删除后调度器清除任务
3. 局限：依赖等待时间，没法放进自动化 CI，只能手工验证

#### Q15｜缺陷你发现了 8 条，根因是什么？

一共四类：

1. 业务逻辑缺陷（最多）：路由覆盖、调度传参错误、查询逻辑问题
2. 代码清理遗留：时区配置缺失、前端页面删了但接口代码没清理
3. 校验 & 环境问题：参数校验缺失、环境依赖问题
4. 体验类缺陷：功能正常，只是使用体验不好

其中 1 个 P0，是定时任务完全无法触发。

#### Q16｜CI 里后端怎么启动的？没有 MySQL 怎么办？

靠降级方案，配置三个环境变量：

1. 数据库降级：切换成 SQLite，不用 MySQL
2. 大模型降级：mock 模式，不调用真实大模型
3. 端口配置：避开 MySQL 端口，快速降级

这样 CI 环境不用装中间件，pytest、playwright 自动化都能正常跑。

#### Q17｜JMeter 压测压了哪些？核心指标是啥？

1. 压测链路：登录→查智能体→新建会话→send→查会话→查定时任务
2. 压测配置：3 并发循环执行
3. 核心指标：错误率 0、send 接口 P95 响应≤3s、TPS 稳定；最终结果达标

#### Q18｜P0/P1/P2 你怎么定义的？

按影响程度划分：

1. P0：核心功能完全不可用，阻塞流程，比如定时任务无法触发
2. P1：核心功能有问题，或者安全漏洞，有绕过方案但风险高
3. P2：功能正常，不影响主流程，只是体验不好

本次：1 个 P0，5 个 P1，2 个 P2

#### Q19｜你觉得这次测试还有什么不足？

两点局限：

1. 自动化方面：定时任务真实触发需要等待时间，CI 没法自动跑，只能手工测
2. 性能方面：只做了小并发压测，本地机器有限，没有测高并发场景

这些都写在测试报告遗留风险，不阻塞上线。

#### Q20｜还可以补什么测试？

可以从三个方向补充：

1. 性能：增加多梯度并发，找到系统性能拐点
2. 安全：当前只测了 Prompt 注入、横向越权，还可以补充 SQL 注入、XSS、CSRF
3. UI 自动化：补充定时任务完整链路，但是 UI 维护成本高，优先选改动影响大的场景
