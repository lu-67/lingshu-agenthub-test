> 前 10 题是软件测试通用高频题（招聘网站、CSDN、牛客网上出现频率最高的）；后 10 题是针对 AgentHub 这个项目的实战追问。
> 每题下面那段话就是面试时可以直接说出口的，不用再翻译成术语。

## 一、通用高频题（Q01 ~ Q10）

### Q01｜软件测试和开发是什么关系？

开发是"造东西的"，测试是"挑毛病的"。我们看问题的角度不一样——开发想的是"怎么实现这个功能"，我想的是"用户这么用会不会出问题"。好的测试不是等开发写完才开始，需求阶段就应该介入，把边界条件、异常路径提前想好，避免开发写完了才发现理解偏了。

### Q02｜常用的用例设计方法有哪些？

主要四种。等价类是把输入分成有效和无效两类挑代表测，比如登录密码分正确、错误、空值。边界值是卡在限制的边上，比如目标字数要求 2~500，我就测 1、2、500、501。场景法是按用户真实操作串一条链路，比如登录→发目标→拿到回答。错误猜测是凭经验猜哪里容易出 bug，比如快速连点两次按钮看看有没有防重入。

### Q03｜HTTP 常见状态码你说几个？

200 成功；301 永久跳转、302 临时跳转；400 参数错、401 没登录、403 没权限、404 资源不存在、405 方法不允许；500 服务端报错、502/503/504 网关/服务不可用/超时。面试常问的就是 200/400/401/403/404/500 这几个。

### Q04｜JWT 鉴权的接口你怎么测？

分三层。第一层是"不带 token"测 401，第二层是"带个假 token"也测 401，第三层是"带普通用户 token 去调 admin 接口"测 403，"带 admin token 调 admin 接口"测 200。我们这个项目 admin 接口全都测了这三层，确保权限不被绕过。

### Q05｜接口测试和 UI 测试的区别？

接口测试是直接调后端接口，不管页面长啥样。能测到的更底层，比如参数校验、越权访问、数据库一致性。UI 测试是在浏览器里点页面，看元素在不在、跳转对不对、权限拦没拦住。UI 测试更直观但更脆（页面一改选择器就坏），接口测试更稳定但看不到页面交互。

### Q06｜接口的异常用例你一般测什么？

四件事。一是参数边界：空值、超长、特殊字符、不合法类型。二是鉴权：无 token、伪造 token、过期 token、越权。三是业务异常：重复提交、并发冲突、数据不存在。四是安全：Prompt 注入、SQL 注入、XSS。

### Q07｜断言是什么？你怎么写？

断言就是"我猜返回应该是什么样，跑的时候检查对不对"。我一般断三层：先断 HTTP 状态码对不对（比如该 200 是不是 200、该 401 是不是 401），再断业务错误码对不对（比如参数非法是 40001、注入被拦是 40002），最后断关键字段在不在（比如登录返回里必须有 token）。

### Q08｜接口之间有关联怎么办？

比如新建会话后拿到的 sessionId 要给 send 接口用。两种方式：Postman 里用环境变量存，每个请求的 Tests 脚本里 `pm.environment.set('sessionId', json.sid)`，后面拼 URL 就直接用 `{{sessionId}}`。Pytest 里用 fixture，或者上一个用例的返回值存到变量里给下一个用例。所以 Postman 集合必须从上往下跑，跳着跑变量是空的。

### Q09｜发现 bug 之后怎么处理？

先确认是不是真 bug——有没有复现、是不是我的环境问题、是不是需求本身就这么设计的。然后写缺陷报告，要写清楚：影响说明（这个 bug 对业务有什么影响）、复现步骤、预期结果、实际结果。严重程度分 P0（核心功能挂了）、P1（核心功能有问题但有临时绕过）、P2（功能能用但体验不好）。修完之后我要跑回归，不能只测那一条，还要测关联模块有没有被带坏。

### Q10｜什么时候可以放行？

三个条件。第一，所有用例必须跑一遍，不能有 P0/P1 级别的未关闭缺陷。第二，回归通过——之前有 bug 的地方修完重测过，而且关联模块也顺带验了。第三，性能达标——错误率 0、P95 在可接受范围、CI 每次 push 都是绿的。这些不是拍脑袋定的，是我先跑了一轮摸底之后，根据真实情况写进测试计划里的通过标准。

## 二、AgentHub 项目实战追问（Q11 ~ Q20）

### Q11｜你这个项目一共多少个接口？覆盖得怎么样？

24 个。分 7 组：健康检查 1 个、登录注册 4 个（含验证码）、智能体 3 个、会话 5 个（核心是 send 那个）、定时任务 4 个、交付物下载 1 个、管理后台 6 个。接口测试 85 条，每个接口至少有正向、鉴权、异常三个维度，admin 接口全部三层权限（无 token 401、普通 token 403、admin 200），Prompt 注入 8 种变体全测了，横向越权也有 3 条。

### Q12｜最核心的 send 接口你怎么测的？

分两大类，正向和异常。正向就是正常目标，断言能返回自然语言回答。异常有七八条：1 字目标（太短）、501 字目标（太长）、七八种 Prompt 注入语句、无 token 401、伪造 token 401、横向越权（用 A 用户的 token 调 B 用户的 send）。每条都断状态码 + 业务错误码（注入被拦会返回 40002）。

### Q13｜Postman 为什么要按顺序跑？

因为后面的请求依赖前面的返回值。比如先登录拿 token 存在 `{{token}}`，然后智能体列表拿第一个 agentId 存在 `{{agentId}}`，然后新建会话拿 sessionId 存在 `{{sessionId}}`，后面 send、approve 都要用到这些。跳着跑的话变量是空的，会返回 404。我特意在 Postman 集合的每个请求的 Tests 脚本里写了存变量的代码，确保从上往下跑的时候变量都对得上。

### Q14｜定时任务接了真实调度器，你怎么测的？

最真实的办法就是真的等时间。建一条每分钟触发的 cron，等 2~3 分钟，刷新列表看"上次运行时间"有没有更新、有没有生成会话记录。建→跑→停→删整条链路都测了：新建后列表里多一条、停用后状态变灰且不再触发、删除后调度器里对应的 job 也没了。另外 JMeter 里也有混合压测的轻量请求。

### Q15｜横向越权你测了什么？

三条核心链路。一是会话详情：用 A 用户登录，直接把 URL 里的 sid 改成 B 用户的，看看能不能读到 B 的会话。二是定时任务停用：用 A 用户的 token 去 PUT B 的 automation，应该返回 404。三是交付物下载：用 A 的 token 去 GET B 的 artifact。全部测到了，后端返回 404（相当于"没找到"而不是"越权"，对普通用户更安全，不会暴露"这个 id 存在但不是你的"）。

### Q16｜缺陷你发现了 8 条，根因是什么？

四类。最多的是功能逻辑缺陷（3 条），比如路由清理不彻底导致级联删除逻辑被覆盖、调度器调执行接口参数不匹配。然后是遗留冗余类（2 条），比如时区配置遗漏、前端删功能没删干净。边界校验（1 条）、环境依赖（1 条）、需求体验（1 条）。P0 就一条：定时任务触发直接报错，整个功能完全不可用。

### Q17｜CI 里后端怎么启动的？

用降级模式。设了三个环境变量：`DB_FALLBACK_SQLITE=1` 让数据库走 SQLite，`AGENT_MODE=mock` 让大模型走 mock，`MYSQL_PORT=33999` 让它连不上 MySQL 快速走降级。所以 CI 环境里不需要装 MySQL、Redis、DeepSeek，后端照样能跑通业务接口，Pytest 的 85 条和 Playwright 的 6 条都能在 CI 里跑。

### Q18｜JMeter 压测压了哪些？核心指标是啥？

6 个请求按依赖顺序：登录→列智能体→建会话→send（核心，挂了 3s 耗时断言）→查会话→列定时任务。3 并发循环 10 次。核心看三个指标：错误率必须是 0、send 接口 P95 不能超 3000ms、TPS 稳定。结果 send 接口 P95 大概在 800~1500ms 之间，错误率 0，达标了。

### Q19｜还可以补什么测试？

三个方向。第一，性能可以加并发梯度：从 3 调到 10、20，看拐点在哪。第二，安全可以加 OWASP Top 10 的其他项，比如 XSS、SQL 注入（目前只覆盖了 Prompt 注入和横向越权）。第三，端到端 UI 自动化可以再加几条，比如定时任务建→跑→停→删的完整链路，但 UI 自动化维护成本高，我只选了改坏了最严重的 6 条。

### Q20｜你觉得这次测试还有什么不足？

两个地方。第一，定时任务的真实触发验证依赖人工等时间，没有自动化手段——最快也要等 2 分钟，CI 里跑不了。第二，性能只压了 3 并发，生产级别的 100+ 没做，因为本地机器扛不住。这两个我都记在了测试报告的遗留风险里，不是阻塞性的，但下个版本可以改进。
