# 灵枢 AgentHub · 测试计划

> 版本 v2.1，更新日期 2026-11-03，负责人：测试工程师

## 一、项目概述

### 1.1 这是什么产品

灵枢 AgentHub 是一个 AI 智能体平台。用户提交一个目标（比如"帮我调研今年宠物智能硬件的市场情况"），平台会自动匹配一个合适的智能体，拆解成几个步骤去执行，最后给用户一份整理好的文字回答和原始数据文件。

### 1.2 本次测试要达成什么

验证这个平台当前版本能不能正常上线给用户使用。重点检查：

1. 用户从登录到给智能体发目标到拿到最终回答，这条主链路能不能顺畅跑完
2. 定时任务能不能按用户设定的时间自动触发执行（不是假的模拟，是真实到点跑）
3. 管理员的权限是不是和普通用户严格隔开，普通用户碰不到管理员的功能
4. 平台能不能识别并拦截"注入型"的恶意目标（比如让智能体说自己的系统提示词）
5. 多个用户之间的数据是不是互相隔离，A 用户看不到 B 用户的东西
6. 性能：并发发请求的时候平台会不会卡死、会不会超时

### 1.3 这次测什么、不测什么

| 会测的 | 不会测的 |
|--------|---------|
| 全部 24 个接口的正常流程和异常流程 | 移动端适配（产品只做桌面端） |

| 登录、注册、验证码 | |

| 对话发送、执行、授权门禁 | |
| 定时任务的建、改、停、删、真实触发 | |
| admin 管理后台：用户列表、详情、删除、统计 | |
| 交付物（CSV / Markdown 文件）下载 | |
| 纵向越权（普通用户调 admin 接口应被拦） | |
| 横向越权（A 用户不能看 B 用户的东西） | |
| prompt 注入拦截（英文、中文、带 emoji 的变体） | |

### 1.4 测试前需要准备好什么

- 服务器能正常访问（包括网站本身、数据库、定时任务调度器都要起来）
- 一份完整的接口清单（入参是什么、返回什么字段、错误时返回什么）
- 两个测试账号：普通用户 tester（密码 tester123）、管理员 admin（密码 admin123）
- Postman 测试集合 + Newman 运行环境
- JMeter 压测脚本
- 缺陷记录的地方（禅道或 GitHub Issues）

## 三、测试策略

### 3.1 用例怎么设计

| 方法 | 说明 | 用在哪 |
|------|------|--------|
| 等价类划分 | 把输入分成"对的"和"不对的"两类，每类挑一个代表来测 | 密码 → 正确密码（对类）/ 错误密码、空密码（不对类） |
| 边界值分析 | 挑限制条件边上的值来测 | 目标字数要求 2~500 字 → 测 1 字、2 字、500 字、501 字 |
| 场景法 | 按用户真实操作，串一条完整的操作链出来 | 登录 → 选智能体 → 发目标 → 等执行 → 下载文件 |
| 错误猜测 | 凭经验猜哪里容易出 bug，专门去测 | 按钮连点两次会不会发两条请求、断网了页面有没有提示、定时任务停用再启用会不会又生效 |

### 3.2 测试分层

| 层级 | 做什么 | 工具 |
|------|--------|------|
| 接口测试（主要） | 24 个接口每个至少一条正常请求 + 一条异常请求 | Postman 集合，Newman 批量跑 |
| 功能测试 | 8 个页面逐个点，看能不能正常操作 | 浏览器手工点 |
| 真实链路验证 | 定时任务等时间看能不能真触发、删用户看关联数据是不是清干净了 | 浏览器 + 查数据库 |

### 3.3 高风险点（最容易出问题的地方）

| 风险 | 为什么说它是风险 | 怎么测 |
|------|-----------------|--------|
| 核心对话链路 | 用户最常用的功能，出了问题平台就没法用了 | 正常目标 → 应该完成；注入语句 → 应该被拦；带"给所有客户发邮件"这种敏感词 → 应该停下来等用户确认 |
| 定时任务真实触发 | 不是假装触发，要等时间推进才能看到效果 | 建一个每分钟触发的任务，等 2~3 分钟，看列表里的"上次运行时间"是不是更新了 |
| 纵向越权 | 普通用户能不能偷偷调管理员的功能 | 用普通用户 token 发全部 6 个管理员接口，全部应该被拦下来 |
| 横向越权 | 甲用户能不能看到或改掉乙用户的东西 | 用 tester 的 token 去查 admin 的会话、定时任务，应该查不到（返回 404） |
| 级联删除 | admin 删一个用户，他名下的智能体、会话、消息、定时任务是不是一起清掉了 | 删完 tester 之后查数据库，tester 创建的所有东西都应该消失 |
| prompt 注入拦截 | 安全关键，用户可能发"忽略之前的指令"想套系统提示词 | 8 种典型注入语句（英文、中文、带 emoji、带引号变体）全部发一遍，应该全被拦 |
| 基础安全（接口暴露） | 有些接口可能忘了加登录校验，匿名就能调 | 不带 token 逐个发请求，需要登录的接口应该全部返回 401 |
| 验证码一次性 | 验证码不能重复使用，否则注册可以无限尝试 | 用同一个验证码注册两次，第二次应该提示"验证码已过期" |
| 兼容性（Edge 浏览器） | 主要验证 Chrome，但 Edge 内核一样，重点验证关键流程不崩 | 在 Edge 浏览器里完整走一遍：登录→发目标→拿到回答→下载文件 |
| 兼容性（高分屏） | 高分屏（2K/4K）可能导致布局错位、按钮变小 | 把屏幕分辨率调到 2560×1440，看导航栏、卡片、按钮有没有错位 |
| 性能瓶颈 | 并发发请求时会不会超时或阻塞 | JMeter 开多个线程同时发目标，看响应时间和失败率 |

### 3.4 缺陷怎么定级

| 级别 | 什么情况算 | 多久修 | 举个例子 |
|------|-----------|--------|---------|
| P0 阻断 | 核心功能没法用，测试也没法继续 | 当天 | 对话接口直接报错、登录完全失效、定时任务一启动就崩 |
| P1 严重 | 核心功能能用但有问题，或者权限绕过、注入没拦住 | 24 小时内 | 注入语句被绕过、删用户没清干净数据、普通用户能进管理员页面 |
| P2 一般 | 功能能用但体验不好，或次要接口有小问题 | 本轮迭代内 | 错误提示不清楚、输入框长度限制没生效、列表分页显示错位 |
| P3 轻微 | 建议性的、不影响主流程 | 有空再改 | 按钮的动画效果、空数据时的图标、加载动画太长 |

### 3.5 除了 HTTP 状态码，还要校验业务码

接口返回体里除了 HTTP 状态码（200、400、401、403、404），还有业务层的 code 和 message，测试时两边都要看：

| 场景 | HTTP 码 | 业务 code | message 应该长什么样 |
|------|--------|-----------|---------------------|
| 没登录就调接口 | 401 | 40101 | 未授权，请先登录 |
| 普通用户调管理员接口 | 403 | 40301 | 权限不足，仅管理员可访问 |
| 提交的数据不合法 | 400 | 40001 | 请求参数不合法 |
| prompt 注入 | 400 | 40002 | 检测到提示词注入，请求已拦截 |
| 查不存在的资源 / 越权查别人的 | 404 | 40401 | 资源不存在 |
| 名字重复（比如注册重名） | 400 | 40003 | 名称已存在 |

### 3.6 回归怎么做

| 什么时候回归 | 回归范围 |
|-------------|---------|
| P0/P1 缺陷修完 | 缺陷所在的模块 + 关联模块（比如修了对话接口，顺带复测会话列表、消息存储、文件下载） |
| P2/P3 缺陷修完 | 只回归有缺陷的那个功能点 |
| 调度器或权限模块有大改动 | 24 个接口全量重跑 + 定时任务真实触发再等一遍时间 |
| 版本打包准备上线前 | 全量接口 + UI 用例 + 定时任务链路完整跑一遍 |

### 3.7 日志要检查什么

| 检查项 | 应该看到什么 |
|--------|-------------|
| 定时任务执行 | 成功时打印任务 ID、什么时候跑的、触发的目标内容；失败时打印任务 ID 和报错信息 |
| 对话接口异常 | 超时或报错时，能看到用户提交的目标、报错原因、执行到第几步出错的 |
| 权限拦截 | 拦了越权请求时，记录请求路径、哪个用户发的、为什么被拦 |

### 3.8 什么时候算测完能放行

1. 24 个接口全部跑过，每个接口至少一条正常 + 一条异常 + 一条鉴权用例
2. 所有断言都通过——包括 HTTP 状态码、业务 code、必填字段、字段值
3. 定时任务真实触发链路验证通过（建→等时间→看到触发→改→停→删全流程）
4. 8 种 prompt 注入全部被拦截
5. 没有 P0 或 P1 缺陷还挂着（P2/P3 可以留作已知风险上线）
6. 管理员纵向越权和用户间横向隔离全部正确拦截

## 五、可能遇到的问题和应对

| 风险 | 影响 | 怎么办 |
|------|------|--------|
| 数据库没启动，接口全报错 | 没法测 | 开始前先访问健康检查接口确认 |
| 定时任务要等时间，耗时长 | 测试慢 | 用每分钟触发的 cron，等 2~3 分钟足够 |
| 对话接口执行需要 1~2 秒，批量跑容易超时 | Newman 报告里误报失败 | Postman / Newman 的超时设到 5 秒 |
| 清理不干净的测试数据导致后续用例失败 | 结果不可靠 | 每轮回归前清掉 tester 账号下的会话、定时任务、文件 |
| 性能压测和功能测试同时跑互相影响 | 两边结果都不准 | 压测和功能测试串行，不要同时跑 |

## 六、什么时候可以开始、什么时候要停下来

### 6.1 开始测试前的准入条件（必须全部满足）

1. 网站、数据库、定时任务调度器都能起来，健康检查返回正常
2. 接口清单（入参、返回字段、错误码）已跟开发确认过，没矛盾
3. 核心链路能手动走通：登录 → 选智能体 → 发目标 → 拿到回答
4. Postman 集合、JMeter 脚本、测试账号已交付，测试人员本地能跑通一次请求
5. 缺陷记录平台已建好，测试人员能创建和关闭缺陷工单

以上任何一条不满足，测试人员可以拒绝开始。

### 6.2 中途停下来的情况

- 出现 1 个以上 P0 缺陷，后面的用例全没法跑了
- 核心服务连续 2 次健康检查失败，环境不可用超过 4 小时
- 接口契约被改了，原来的测试用例全部失效

**恢复条件**：导致暂停的问题解决了，冒烟链路（登录 → 发目标）重新走通。

### 6.3 测试数据怎么管理

| 什么时候 | 做什么 |
|---------|--------|
| 测试开始前 | tester 账号下预先建好 1 个智能体 + 1 条每分钟触发的定时任务（用来验证级联删除） |
| 每轮回归前 | 清掉 tester 账号下所有会话、定时任务、交付物；admin 账号不动 |
| 发现 P0/P1 缺陷后 | 不要删触发缺陷的那批数据，留着等修复验证通过再清 |

## 七、缺陷怎么处理

### 生命周期

**新建 → 分派 → 修复中 → 待验证 → 已关闭**。验证没通过就退回修复中，重新走一遍流程。

### 每条缺陷工单必须有的字段

- 缺陷编号、标题、所属功能模块
- 严重程度（P0~P3）、优先级
- 复现前置条件、一步步的复现步骤、预期是什么、实际是什么
- 发现日期、分配给谁修
- 修复版本号、回归验证结果、关闭日期

### 处理约定

- 缺陷提交当天定级
- 开发修完要标注修复版本号
- 关闭必须测试人员验证通过，开发不能自己关
